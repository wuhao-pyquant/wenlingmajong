# Zeabur 线上大厅设计

日期：2026-07-07

## 背景

当前项目是局域网可信环境下的温岭麻将主机：一个 Python HTTP 服务、一个全局 `BattleSession`、SQLite 账号/战绩数据、静态浏览器大厅和牌桌。线上部署到 Zeabur 后，原来的“可信 LAN + 选择账号登录 + 本机管理接口”不再成立，需要改成互联网可用的账号、权限、房间和管理模型。

本设计的目标是先支持小规模熟人局：最多同时 2-3 桌，使用简单邀请码注册，管理员可管理账号、邀请码、房间和在线访问用户。第一版不追求大规模平台化，不做多实例横向扩容。

## 目标

- 部署到 Zeabur 中国可访问站点。
- 支持密码注册和登录。
- 注册必须使用简单邀请码。
- 管理员可以生成、停用和查看邀请码使用情况。
- 管理员可以监控当前访问用户，包括登录用户和未登录访客。
- 支持最多 3 个活动房间。
- 创建房间者自动成为房主。
- 大厅展示房间、座位、状态和 AI 等级。
- 房主可以在允许阶段管理自己的房间。
- 对局中允许房主或管理员二次确认后关闭整个房间。
- UI 从局域网工具页升级为成熟棋牌游戏大厅风格。

## 非目标

- 不保留当前账号、战绩或房间数据。
- 不迁移旧数据库。
- 不引入 FastAPI、前端构建式 SPA 或大型框架重写。
- 不做多服务实例或横向扩容。
- 不做支付、公开匹配、排行榜、好友系统或运营活动。
- 不让邀请码创建管理员账号。

## 推荐方案

采用最小线上化重构：

- 保留当前 Python 标准库 HTTP 服务。
- 保留静态 HTML/CSS/JS 前端。
- 保留现有 `BattleSession` 牌局逻辑。
- 新增 `RoomManager` 管理最多 3 个 `BattleRoom`。
- 每个 `BattleRoom` 内部持有一个独立 `BattleSession`。
- SQLite 作为第一版数据库，Zeabur 上挂载持久化卷。
- 通过环境变量配置端口、数据目录、管理员账号、初始邀请码和房间上限。

这个方案最适合 Zeabur 的小规模部署：运行时资源可控，改动集中，能先把公网账号、多房间和大厅跑通。后续如果超过 3 桌或需要多实例，再迁移到 PostgreSQL、Redis 和框架化后端。

## 运行架构

服务启动后创建以下核心对象：

- `BattleApplication`：HTTP 应用入口、配置、数据库、会话和静态文件服务。
- `BattleDatabase`：全新线上 SQLite schema。
- `AuthService`：密码哈希、登录、bearer token、角色校验。
- `InviteCodeService`：邀请码生成、验证、停用和使用次数统计。
- `PresenceTracker`：记录登录用户和未登录访客的当前访问状态。
- `RoomManager`：创建、关闭、查询和路由房间。
- `BattleRoom`：房间元数据、房主、AI 等级、关闭状态和 `BattleSession`。

请求流：

1. 未登录用户访问登录/注册页。
2. 注册时提交用户名、密码和邀请码。
3. 登录成功后进入游戏大厅。
4. 大厅接口返回活动房间列表和公开座位状态。
5. 玩家创建房间或加入已有房间。
6. 牌桌接口携带 `room_id`，服务端通过 `RoomManager` 找到对应 `BattleSession`。
7. 房间关闭时，牌桌客户端收到关闭状态并回到大厅。

## 账号和权限模型

### 账号字段

`accounts` 使用全新 schema：

- `account_name`：用户名和显示名，支持中文。
- `password_hash`：密码哈希，不保存明文。
- `role`：`player` 或 `admin`。
- `enabled`：是否允许登录。
- `is_ai`：固定 AI 系统账号标记。
- `created_at`：创建时间。
- `last_login_at`：最近登录时间。

固定 AI 账号由系统初始化，不能登录、不能注册、不能被邀请码影响。

### 注册

普通用户注册必须提供：

- 用户名
- 密码
- 邀请码

邀请码有效且账号名未占用时，创建 `player` 账号。管理员账号不能通过普通注册产生。

### 管理员初始化

服务启动读取：

- `WENLING_ADMIN_USERNAME`
- `WENLING_ADMIN_PASSWORD`

如果管理员不存在则创建；如果存在则保证角色为 `admin` 且启用。密码以环境变量中的值为准，便于 Zeabur 后台重置首个管理员。

### 会话

登录成功后签发随机 bearer token。第一版 token 存在服务内存中，服务重启后用户需要重新登录。所有敏感接口先解析 token，再检查角色或房主身份。

## 邀请码模型

新增 `invite_codes` 表：

- `code`：4-6 位简单短码，例如 `7392`、`WL8K2`。
- `enabled`：是否可用。
- `max_uses`：允许使用次数；为空表示不限次数。
- `used_count`：已使用次数。
- `created_by`：创建管理员。
- `created_at`：创建时间。
- `disabled_at`：停用时间。

管理员后台能力：

- 生成邀请码。
- 设置使用次数上限。
- 停用邀请码。
- 查看使用次数。

服务启动可从 `WENLING_INVITE_CODES` 初始化第一批邀请码。之后主要通过管理员后台维护。

## 在线访问监控

新增内存级 `PresenceTracker`，记录当前访问状态：

- 访问者 ID。
- 是否登录。
- 登录账号。
- 角色。
- 当前页面。
- 所在房间。
- 所在座位。
- IP。
- 浏览器 user agent。
- 最近访问时间。

管理员后台展示当前在线和最近访问用户。监控只显示公开状态，不暴露其他玩家手牌或隐藏信息。登录、登出、管理操作和关闭房间等关键行为可以写入审计日志；普通页面心跳和轮询只保存在内存中，避免 SQLite 写入压力过大。

## 多房间模型

全站最多 3 个活动房间，默认由 `WENLING_MAX_ROOMS=3` 控制。

`BattleRoom` 字段：

- `room_id`：短 ID。
- `room_name`：房间名。
- `owner_account`：房主账号。
- `ai_policy`：房间统一 AI 等级，`low` 或 `high`。
- `created_at`：创建时间。
- `last_active_at`：最近活动时间。
- `status`：`waiting`、`playing`、`round_over`、`closing`、`closed`。
- `session`：独立 `BattleSession`。

规则：

- 登录玩家可以创建房间。
- 创建者自动成为房主。
- 同一玩家同时只能拥有 1 个活动房间。
- 普通玩家可以加入任意未关闭房间。
- 空座继续由 AI 补位。
- 至少 1 名真人入座并准备后可开始。
- 大厅展示所有未关闭房间。

## 房主和管理员权限

### 普通玩家

- 注册和登录。
- 创建 1 个活动房间。
- 加入房间。
- 入座、离座、准备。
- 执行牌局动作。
- 查看公开大厅和自己牌桌状态。

### 房主

房主只能管理自己创建的房间。

`waiting` 和 `round_over` 阶段：

- 踢出玩家。
- 调整房间 AI 等级。
- 修改房间名。
- 关闭房间。

`playing` 阶段：

- 不能踢人。
- 不能换座。
- 不能调整 AI 等级。
- 可以二次确认后关闭整个房间。

对局中关闭房间后，本局作废，所有玩家回到大厅，旧房间不可继续操作。

### 管理员

- 管理账号。
- 管理邀请码。
- 查看在线访问用户。
- 查看所有房间。
- 踢任意房间玩家。
- 关闭任意房间。
- 处理异常占座和卡死房间。

## UI 设计

### 登录和注册页

不再选择已有账号。页面提供：

- 用户名。
- 密码。
- 登录按钮。
- 注册区：用户名、密码、邀请码。
- 中文优先文案。

视觉上作为棋牌游戏入口，不做营销式落地页。

### 游戏大厅

大厅包含：

- 当前账号、角色、在线状态和退出登录。
- 房间卡片列表。
- 创建房间按钮。
- 房间状态徽标。
- 房主、真人人数、座位缩略图、AI 等级。
- 达到 3 个活动房间时禁用创建按钮。

房主在自己的房间卡片或详情面板中看到房主管理入口。

### 牌桌页

继续复用当前牌桌布局和动画。新增：

- 返回大厅。
- 房间关闭提示。
- 房主管理菜单。
- 对局中关闭房间的二次确认。
- `room_id` 感知，所有牌桌 API 路由到对应房间。

### 管理员后台

后台包含：

- 账号管理。
- 邀请码管理。
- 房间管理。
- 在线访问监控。

普通玩家看不到后台入口，直接访问后台接口会返回权限错误。

## Zeabur 部署

服务读取 Zeabur 环境变量：

- `PORT`：服务监听端口，本地默认 `8765`。
- `WENLING_DATA_DIR`：线上数据目录，建议 `/data`。
- `WENLING_PUBLIC_BASE_URL`：公网访问地址。
- `WENLING_ADMIN_USERNAME`：初始化管理员账号。
- `WENLING_ADMIN_PASSWORD`：初始化管理员密码。
- `WENLING_INVITE_CODES`：初始化邀请码列表。
- `WENLING_MAX_ROOMS`：默认 `3`。
- `WENLING_DEFAULT_AI_POLICY`：默认 `low`。
- `WENLING_ALLOW_PUBLIC_REGISTER`：默认允许邀请码注册。

Zeabur 上配置 `/data` 持久化卷，SQLite 数据库、日志和备份都放在该目录。第一版只运行单服务实例，因为 SQLite 和内存房间状态不适合横向多实例。

资源策略：

- 房间上限固定为 3。
- 默认 AI 为低级。
- 高级 AI 可选，但记录决策耗时。
- 增加运行诊断：活动房间数、在线用户数、等待连接数、AI 耗时和慢请求。
- 通过 Zeabur Metrics 观察 CPU、内存和网络。
- 如果 CPU 长期接近 80% 或高级 AI 延迟明显，再提高服务资源或迁移到 Dedicated Server。

## 数据库初始化

线上版不保留当前账号及数据。首次启动创建全新 SQLite 数据库：

- `accounts`
- `battle_stats`
- `invite_codes`
- `audit_events`
- 可选 `room_history`

初始化动作：

- 创建固定 AI 系统账号。
- 创建或更新管理员账号。
- 从环境变量创建初始邀请码。
- 不做旧库迁移兼容。

## API 变更方向

新增大厅和管理接口：

- `GET /api/lobby/rooms`
- `POST /api/lobby/rooms`
- `POST /api/lobby/rooms/{room_id}/close`
- `POST /api/lobby/rooms/{room_id}/settings`
- `GET /api/admin/accounts`
- `POST /api/admin/accounts/{account}/disable`
- `POST /api/admin/accounts/{account}/reset-password`
- `GET /api/admin/invite-codes`
- `POST /api/admin/invite-codes`
- `POST /api/admin/invite-codes/{code}/disable`
- `GET /api/admin/presence`

现有牌桌接口增加 `room_id`：

- `GET /api/battle/{room_id}/state`
- `GET /api/battle/{room_id}/wait`
- `POST /api/battle/{room_id}/sit`
- `POST /api/battle/{room_id}/leave`
- `POST /api/battle/{room_id}/ready`
- `POST /api/battle/{room_id}/action`
- `POST /api/battle/{room_id}/report-bug`

可以保留旧路径一段时间用于本地开发，但线上 UI 使用新路径。

## 风险和缓解

- 高级 AI 可能消耗 CPU：默认低级 AI，记录高级 AI 耗时，房间上限固定为 3。
- SQLite 不适合多实例：第一版明确单服务实例，未来扩容再迁 PostgreSQL。
- 内存 token 重启失效：第一版接受重新登录，降低实现复杂度。
- 管理员密码环境变量泄露风险：只通过 Zeabur 环境变量配置，不写入仓库。
- 在线监控写入过多：访问心跳保存在内存，关键审计事件才写 SQLite。
- 对局中关闭影响玩家体验：必须二次确认，并在 UI 中明确提示本局作废。
